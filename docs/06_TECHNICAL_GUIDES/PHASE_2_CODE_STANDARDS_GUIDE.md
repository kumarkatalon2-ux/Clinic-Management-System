1.1 ENDPOINT NAMING CONVENTIONS
──────────────────────────────────────────────────────────────────────────────

PATTERN:
  /api/v{version}/{resource}/{id}/{action}

EXAMPLES:

  ✓ GET /api/v1/patients/123
    └─ Fetch single patient

  ✓ GET /api/v1/patients?status=active&page=1&limit=20
    └─ List patients with filtering

  ✓ POST /api/v1/appointments
    └─ Create new appointment

  ✓ PUT /api/v1/appointments/456
    └─ Update appointment

  ✓ DELETE /api/v1/appointments/456
    └─ Delete appointment

  ✓ POST /api/v1/consultations/789/finalize
    └─ Custom action (finalize consultation)

  ✓ GET /api/v1/patients/123/lab-results
    └─ Related resource (patient's lab results)

NAMING RULES:

  Resource Names:
    • Use lowercase: /api/v1/patients (not /Patients)
    • Use plural: /api/v1/patients (not /patient)
    • Use hyphens for multi-word: /api/v1/lab-results (not /labResults)
    • Use meaningful terms: /api/v1/consultations (not /consults)

  Query Parameters:
    • Use lowercase: ?status=active (not ?Status=active)
    • Use camelCase: ?orderBy=date (not ?order_by=date)
    • Use meaningful names: ?status, ?limit, ?offset, ?search

  HTTP Methods:
    • GET: Retrieve resources (safe, idempotent)
    • POST: Create resources (not idempotent)
    • PUT: Update entire resource (idempotent)
    • PATCH: Partial update (idempotent, if supported)
    • DELETE: Remove resources (idempotent)

  Versioning:
    • Include version in URL: /api/v1/, /api/v2/
    • Increment for breaking changes
    • Support previous version for 6 months
    • Current: v1, Plan v2 after Phase 3

REQUIRED HEADERS:

  Authorization: Bearer {JWT_token}
    └─ All authenticated endpoints require this
    └─ Format: "Bearer {token}"
    └─ Token format: JWT with 1-hour expiration

  Content-Type: application/json
    └─ All request bodies must be JSON
    └─ Accept: application/json (expected response)

  X-Request-ID: UUID
    └─ Unique identifier for request tracking
    └─ Used in logs and error responses
    └─ Generated by client or API gateway if missing

  X-Tenant-ID: string (Multi-tenant systems)
    └─ Required for multi-tenant endpoints
    └─ Validates user has access to tenant
    └─ Example: "tenant_clinic_123"

OPTIONAL HEADERS:

  Accept-Language: en-US
    └─ For localized responses (future enhancement)

  X-Idempotency-Key: UUID
    └─ For idempotent operations (POST creates)
    └─ Prevents duplicate records on retry

REQUEST VALIDATION:

  RULE: All input must be validated
    ✓ Type checking (string, number, boolean, date)
    ✓ Range validation (min/max)
    ✓ Format validation (email, phone, UUID)
    ✓ Business logic validation (appointment in future)

1.4 PAGINATION STANDARDS
──────────────────────────────────────────────────────────────────────────────

PARAMETERS:

  page: number (default: 1)
    └─ 1-indexed page number
    └─ Minimum: 1
    └─ Example: ?page=2

  limit: number (default: 20, max: 100)
    └─ Records per page
    └─ Minimum: 1
    └─ Maximum: 100 (prevent large data pulls)
    └─ Example: ?limit=50

  offset: number (alternative to page)
    └─ For cursor-based pagination
    └─ Offset from start: ?offset=40&limit=20
    └─ Use page-based (simpler) by default

  sortBy: string (default: createdAt)
    └─ Field to sort by
    └─ Example: ?sortBy=name

  sortOrder: string (asc|desc, default: desc)
    └─ Sort direction
    └─ Example: ?sortOrder=asc

RESPONSE PAGINATION OBJECT:

  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 145,           // Total records
    "pages": 8,             // Total pages
    "hasNext": true,        // Has more pages
    "hasPrev": false        // Has previous pages
  }

EXAMPLE QUERIES:

  # Get first 20 patients
  GET /api/v1/patients?page=1&limit=20

  # Get page 3 (records 40-59)
  GET /api/v1/patients?page=3&limit=20

  # Sort by name, ascending
  GET /api/v1/patients?sortBy=firstName&sortOrder=asc

  # Combine filters and pagination
  GET /api/v1/patients?status=active&page=1&limit=20&sortBy=createdAt

2.1 HTTP STATUS CODES
──────────────────────────────────────────────────────────────────────────────

SUCCESS CODES:

  200 OK
    └─ Standard successful response
    └─ Used for: GET, PUT, PATCH, DELETE

  201 Created
    └─ Resource successfully created
    └─ Used for: POST requests
    └─ Include Location header: Location: /api/v1/appointments/apt_123

  202 Accepted
    └─ Request accepted but not yet processed
    └─ Used for: Async operations (long-running tasks)
    └─ Include status endpoint: /api/v1/tasks/task_123/status

  204 No Content
    └─ Successful response with no content
    └─ Used for: DELETE requests (optionally)

CLIENT ERROR CODES:

  400 Bad Request
    └─ Invalid request format or validation failure
    └─ When: Malformed JSON, missing required fields, invalid types
    └─ Example: POST with invalid appointmentType

  401 Unauthorized
    └─ Missing or invalid authentication
    └─ When: No Authorization header, expired token, invalid token
    └─ Response: Include WWW-Authenticate header

  403 Forbidden
    └─ Authenticated but not authorized
    └─ When: User doesn't have permission to resource (RBAC)
    └─ Example: Provider accessing another clinic's data

  404 Not Found
    └─ Resource doesn't exist
    └─ When: Invalid ID, deleted resource
    └─ Example: GET /appointments/invalid_id

  409 Conflict
    └─ Request conflicts with current state
    └─ When: Duplicate creation, status transition invalid
    └─ Example: Finalize already finalized consultation

  422 Unprocessable Entity
    └─ Validation error on business logic
    └─ When: Valid format but fails business rules
    └─ Example: Appointment in past, patient already has consultation

  429 Too Many Requests
    └─ Rate limit exceeded
    └─ When: Exceeded requests per hour
    └─ Response: Include Retry-After header

SERVER ERROR CODES:

  500 Internal Server Error
    └─ Unexpected server error
    └─ When: Uncaught exception, database error, etc.
    └─ Response: Include request ID for debugging

  503 Service Unavailable
    └─ Server temporarily unavailable
    └─ When: Maintenance, dependent service down
    └─ Response: Include Retry-After header

2.3 ERROR HANDLING IN CODE
──────────────────────────────────────────────────────────────────────────────

PATTERN: Try-Catch with Proper Error Response

  async function getAppointment(req, res, next) {
    try {
      const { id } = req.params;
      
      // Validate input
      if (!isValidUUID(id)) {
        return res.status(400).json({
          success: false,
          error: {
            code: "INVALID_REQUEST",
            message: "Invalid appointment ID format",
            statusCode: 400,
            requestId: req.id
          }
        });
      }
      
      // Fetch appointment
      const appointment = await Appointment.findById(id);
      if (!appointment) {
        return res.status(404).json({
          success: false,
          error: {
            code: "APPOINTMENT_NOT_FOUND",
            message: `Appointment with ID '${id}' not found`,
            statusCode: 404,
            requestId: req.id
          }
        });
      }
      
      // Check authorization
      if (!userHasAccess(req.user, appointment)) {
        return res.status(403).json({
          success: false,
          error: {
            code: "FORBIDDEN",
            message: "You do not have permission to access this appointment",
            statusCode: 403,
            requestId: req.id
          }
        });
      }
      
      // Success response
      return res.status(200).json({
        success: true,
        data: appointment,
        meta: { requestId: req.id, timestamp: new Date().toISOString() }
      });
      
    } catch (error) {
      logger.error('Error fetching appointment', {
        error: error.message,
        stack: error.stack,
        requestId: req.id
      });
      
      return res.status(500).json({
        success: false,
        error: {
          code: "INTERNAL_ERROR",
          message: "An unexpected error occurred",
          statusCode: 500,
          requestId: req.id
        }
      });
    }
  }

PATTERN: Error Handling Middleware

  function errorHandler(err, req, res, next) {
    const statusCode = err.statusCode || 500;
    const errorCode = err.code || 'INTERNAL_ERROR';
    const message = err.message || 'An unexpected error occurred';
    
    logger.error('Request error', {
      error: errorCode,
      message: message,
      statusCode: statusCode,
      requestId: req.id,
      stack: err.stack
    });
    
    res.status(statusCode).json({
      success: false,
      error: {
        code: errorCode,
        message: message,
        statusCode: statusCode,
        requestId: req.id,
        timestamp: new Date().toISOString(),
        ...(err.details && { details: err.details })
      }
    });
  }

  // Use in Express
  app.use(errorHandler);

3.1 LOGGING LEVELS
──────────────────────────────────────────────────────────────────────────────

SEVERITY LEVELS:

  DEBUG (Level 0)
    └─ Detailed debugging information
    └─ Used in development, not production
    └─ Example: "Query parameters: {...}"

  INFO (Level 1)
    └─ General informational messages
    └─ Normal application flow
    └─ Example: "Appointment created successfully"

  WARN (Level 2)
    └─ Warning messages for potential issues
    └─ Usually not errors but worth noting
    └─ Example: "Slow query detected: 2500ms"

  ERROR (Level 3)
    └─ Error messages
    └─ Something went wrong
    └─ Example: "Database connection failed"

  FATAL (Level 4)
    └─ Critical errors
    └─ System must be shut down
    └─ Example: "Out of memory"

  function requestLoggingMiddleware(req, res, next) {
    req.startTime = Date.now();
    
    // Log request
    logger.info('Incoming request', {
      requestId: req.id,
      method: req.method,
      path: req.path,
      userId: req.user?.id,
      tenantId: req.headers['x-tenant-id']
    });
    
    // Log response
    const originalJson = res.json;
    res.json = function(data) {
      const duration = Date.now() - req.startTime;
      
      logger.info('Request completed', {
        requestId: req.id,
        method: req.method,
        path: req.path,
        statusCode: res.statusCode,
        duration: duration,
        userId: req.user?.id
      });
      
      return originalJson.call(this, data);
    };
    
    next();
  }

    // Provider completes consultation
    await finalizeconsultation(apt.id);
    
    // Insurance claim auto-created
    const claim = await getInsuranceClaim(apt.id);
    expect(claim.status).toBe('PENDING_REVIEW');
  });

6. SECURITY STANDARDS

6.1 AUTHENTICATION & AUTHORIZATION
──────────────────────────────────────────────────────────────────────────────

AUTHENTICATION FLOW:

  1. User logs in (email + password)
  2. System validates credentials
  3. System generates JWT token (1-hour expiration)
  4. Client stores token (memory/localStorage)
  5. Client includes token in all subsequent requests
     Authorization: Bearer {token}
  6. Server validates token on every request
  7. If invalid/expired, return 401

JWT PAYLOAD:

  {
    "sub": "user_123",              // User ID
    "email": "john@example.com",
    "tenantId": "clinic_123",       // Multi-tenant
    "roles": ["provider", "admin"],
    "permissions": [
      "appointments:read",
      "appointments:write",
      "consultations:write"
    ],
    "iat": 1612345600,              // Issued at
    "exp": 1612349200,              // Expires (1 hour)
    "iss": "clinical-system"        // Issuer
  }

AUTHORIZATION PATTERN:

  async function getAppointment(req, res) {
    const appointment = await Appointment.findById(req.params.id);
    
    // Check ownership (multi-tenant)
    if (appointment.clinicId !== req.user.tenantId) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    
    // Check permissions (RBAC)
    if (!req.user.permissions.includes('appointments:read')) {
      return res.status(403).json({ error: 'Insufficient permissions' });
    }
    
    res.json({ success: true, data: appointment });
  }

6.2 INPUT VALIDATION & SANITIZATION
──────────────────────────────────────────────────────────────────────────────

VALIDATION PATTERN:

  import { validate, isEmpty, isEmail } from 'class-validator';
  
  class CreateAppointmentDTO {
    @IsNotEmpty()
    @IsUUID()
    clinicId: string;
    
    @IsNotEmpty()
    @IsUUID()
    patientId: string;
    
    @IsNotEmpty()
    @IsISO8601()
    startTime: string;
    
    @IsOptional()
    @Length(0, 500)
    notes: string;
  }
  
  async function createAppointment(req, res) {
    const dto = plainToClass(CreateAppointmentDTO, req.body);
    const errors = await validate(dto);
    
    if (errors.length > 0) {
      return res.status(400).json({ error: 'Validation failed', details: errors });
    }
    
    // Process validated data
  }

COMMON VALIDATIONS:

  ✓ Required fields: @IsNotEmpty()
  ✓ Email format: @IsEmail()
  ✓ UUID format: @IsUUID()
  ✓ Date format: @IsISO8601()
  ✓ String length: @Length(min, max)
  ✓ Number range: @Min(), @Max()
  ✓ Enum: @IsEnum(StatusEnum)

6.3 SQL INJECTION PREVENTION
──────────────────────────────────────────────────────────────────────────────

VULNERABLE CODE (DO NOT USE):

  ❌ DON'T:
  const query = `SELECT * FROM appointments WHERE id = '${req.params.id}'`;
  const result = await db.query(query);

SECURE CODE (USE THIS):

  ✅ DO:
  const query = 'SELECT * FROM appointments WHERE id = $1';
  const result = await db.query(query, [req.params.id]);

PATTERN: Parameterized Queries

  // Using parameterized queries (all frameworks support this)
  const appointment = await db.query(
    'SELECT * FROM appointments WHERE clinic_id = $1 AND status = $2',
    [clinicId, status]
  );

7.1 RESPONSE TIME TARGETS

TARGET RESPONSE TIMES:

  Search operations:                    < 1000ms
  Complex business logic:               < 2000ms

MEASURING:

  app.use((req, res, next) => {
    const startTime = Date.now();
    
    res.on('finish', () => {
      const duration = Date.now() - startTime;
      logger.info('Request timing', {
        method: req.method,
        path: req.path,
        statusCode: res.statusCode,
        duration: duration
      });
      
      // Alert if slow
      if (duration > 2000) {
        logger.warn('Slow request detected', {
          duration,
          method: req.method,
          path: req.path
        });
      }
    });
    
    next();
  });

──────────────────────────────────────────────────────────────────────────────

INDEXING STRATEGY:

  SELECT * FROM appointments;  // Fetches all columns

  SELECT id, clinic_id, patient_id, status, start_time

  WHERE clinic_id = $1 AND status = $2
  LIMIT 20 OFFSET 0;

    ✓ Create consultation → invalidate appointment cache

8.3 MULTI-TENANCY
──────────────────────────────────────────────────────────────────────────────

PATTERN: Tenant ID in Every Table

  CREATE TABLE appointments (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,  ← Required
    clinic_id UUID NOT NULL,
    patient_id UUID NOT NULL,
    ...
    FOREIGN KEY (tenant_id) REFERENCES tenants(id)
  );

QUERY PATTERN (Always Include Tenant):

  SELECT * FROM appointments
  WHERE tenant_id = $1 AND clinic_id = $2;
    ← Filter by tenant first, then clinic

ROWS LEVEL SECURITY (Optional):

  ALTER TABLE appointments ENABLE ROW LEVEL SECURITY;
  
  CREATE POLICY tenant_isolation ON appointments
    USING (tenant_id = current_setting('app.current_tenant')::uuid);
