1. OBJECTIVE
================================================================================

Design and implement comprehensive backup and disaster recovery (DR) strategy
that ensures business continuity, data protection, compliance with HIPAA/GDPR
regulations, and rapid recovery from infrastructure failures, security breaches,
or data corruption incidents.

Key Goals:
- Backup all critical data (database, files, configurations)
- Achieve RTO (Recovery Time Objective) <4 hours for critical services
- Achieve RPO (Recovery Point Objective) <1 hour (hourly backups)
- Implement redundant backup copies across regions
- Test recovery procedures monthly
- Maintain 7-year backup retention (HIPAA requirement)
- Encrypt all backup data (at-rest and in-transit)
- Automate backup and recovery processes
- Document disaster recovery procedures

Scope:
- Database backups (full, incremental, point-in-time)
- File/document backups (patient attachments, reports)
- Configuration backups (code, infrastructure-as-code)
- Backup verification and testing
- Disaster recovery runbooks
- Failover procedures
- Data restoration procedures

2. BACKUP STRATEGY
================================================================================

2.1 BACKUP ARCHITECTURE
-----------------------

Multi-layer Backup Approach:

Tier 1: Production Database Backups
- Frequency: Hourly
- Type: Incremental snapshots + daily full backup
- Retention: 30 days hot, 2 years cold storage
- Location: S3 (primary region)
- Redundancy: S3 replication to secondary region (every 6 hours)
- Encryption: AES-256 at rest, TLS in transit

Tier 2: Application Data (Uploaded Files)
- Frequency: Continuous (real-time sync to S3)
- Type: Versioned object storage
- Retention: Match database (30 days hot, 2 years cold)
- Location: S3 with versioning enabled
- Redundancy: S3 cross-region replication
- Encryption: AES-256

Tier 3: Configuration & Code
- Frequency: On deployment (automatic)
- Type: Full snapshots
- Retention: 1 year (all deployments)
- Location: Git repository + S3 archive
- Redundancy: Multiple Git remotes
- Encryption: GPG signed

Tier 4: Point-in-Time Recovery (PITR)
- Frequency: Continuous WAL archiving (PostgreSQL)
- Type: Write-ahead logs + snapshots
- Retention: 7 days (operational window)
- Location: S3 + local storage
- Redundancy: Cross-region replication
- Encryption: AES-256

2.2 DATABASE BACKUP WORKFLOW
----------------------------

PostgreSQL Backup Strategy:

1. Daily Full Backup (Midnight UTC)
   - pg_basebackup creates filesystem snapshot
   - Compressed with gzip
   - Uploaded to S3 daily_backups/ folder
   - Size: ~50GB per backup (compressed 15GB)
   - Duration: 15 minutes (parallel jobs)
   - Retention: 30 days

2. Hourly Incremental Backup
   - WAL (Write-Ahead Log) files continuously archived
   - WAL segment size: 16MB
   - Archived every minute to S3 (wal_archive/ folder)
   - Retention: 7 days (for PITR)
   - RPO: Up to 1 minute (last WAL segment)

3. Backup Verification
   - Checksum verification of backup file
   - Restore test on staging DB weekly
   - Catalog of backups maintained in DynamoDB
   - Failed backups trigger alert

Backup Job Workflow:
```
1. Initiate backup (started at 00:00 UTC)
2. Lock database (brief, 1-2 seconds)
3. Snapshot filesystem
4. Release lock
5. Compress snapshot (10 minutes)
6. Upload to S3 (5 minutes)
7. Verify checksum (1 minute)
8. Update backup catalog
9. Replicate to secondary region (6 hours, async)
10. Cleanup old backups (>30 days)
```

2.3 FILE/DOCUMENT BACKUP
------------------------

Patient Attachments & Reports:
- Uploaded to S3 immediately
- S3 versioning enabled (retain all versions)
- Automatic replication to secondary region
- Retention: 7 years (legal requirement)
- Cold storage: Glacier after 1 year

Workflow:
```
1. Patient uploads file
2. File scanned for malware
3. File encrypted
4. Stored in S3 (primary region)
5. S3 triggers Lambda function
6. Lambda replicates to secondary region
7. Record stored in database
8. Notification sent to patient/provider
```

2.4 CONFIGURATION BACKUP
------------------------

Application Configuration:
- Environment files (.env)
- Database connection strings (secrets)
- API keys and credentials (AWS Secrets Manager)
- Infrastructure-as-code (Terraform, CloudFormation)
- Deployment manifests (Kubernetes YAML)

Backup:
- All configuration stored in Git (private repo)
- Secrets encrypted in transit and storage
- Configuration versioning (semantic versioning)
- Backup on each deployment (automatic)
- Retention: 1 year (all versions)

Restore:
- Roll back Git to specific commit
- Redeploy infrastructure from code
- Restore secrets from AWS Secrets Manager
- Application starts with restored config

2.5 BACKUP RETENTION POLICY
---------------------------

HIPAA Requirement: 7-year retention of medical records

Retention Schedule:
- Daily backups: Keep 30 days (hot storage)
- Weekly backups: Keep 13 weeks (monthly summary)
- Monthly backups: Keep 7 years (cold storage)
- Yearly backups: Keep 10 years (compliance archival)

Storage Tiers:
- Hot (S3 standard): 30 days, <100ms access
- Warm (S3 Infrequent): 30-365 days, <1s access
- Cold (Glacier): 1-7 years, <5 minutes access
- Archive (Deep Archive): 7+ years, <12 hours access

Cost Optimization:
- 30 days: $23/TB/month (standard)
- 1 year: $4.10/TB/month (Infrequent)
- 7 years: $1/TB/month (Glacier)
- 10 years: $0.36/TB/month (Deep Archive)

Deletion Policy:
- After 7 years: Medical records deleted (unless legal hold)
- Secure deletion: 3-pass overwrite or cryptographic erasure
- Audit trail: Log all deletions for compliance
- Verification: Confirm deletion succeeded

3. DISASTER RECOVERY SCENARIOS
================================================================================

3.1 RECOVERY TIME OBJECTIVES (RTO)
----------------------------------

RTO by Severity:

Tier 1 (CRITICAL - RTO <4 hours):
- Database complete failure → RTO 2 hours
- Primary data center down → RTO 1 hour (auto-failover)
- API server failure → RTO 30 minutes (auto-scaling)
- Authentication service down → RTO 2 hours

Tier 2 (HIGH - RTO <24 hours):
- Single server failure → RTO 30 minutes
- Data corruption → RTO 4 hours (restore from snapshot)
- DDoS attack → RTO 2 hours (cleanup + restart)
- Security breach → RTO 24 hours (forensic analysis)

Tier 3 (MEDIUM - RTO <7 days):
- Secondary data center issues → RTO 48 hours
- Partial data loss → RTO 24 hours (identify and restore)

3.2 RECOVERY POINT OBJECTIVES (RPO)
-----------------------------------

RPO: Maximum acceptable data loss

Database: RPO 1 hour
- Hourly backups + WAL archiving
- Can restore to any point in last 7 days
- Latest backup <1 hour old

Files: RPO 1 minute
- Continuous S3 sync
- Real-time replication
- Latest version always available

Configuration: RPO 0 (on deployment)
- Git commits captured immediately
- No data loss (versioned)

Business Data: RPO 1 hour
- Matches database backup frequency

3.3 SCENARIO: DATABASE FAILURE
------------------------------

Scenario: PostgreSQL database completely corrupted / unrecoverable

Detection (Automated):
- Healthcheck fails (3 consecutive failures = alert)
- ERROR logs spike
- Query timeouts

Response:
1. Alert triggers (CRITICAL severity)
2. On-call engineer paged immediately
3. Assess damage (can database be restarted?)
4. If yes: pg_ctl restart (attempt recovery)
5. If no: proceed to recovery

Recovery Process (RTO: 2 hours):
1. Identify latest good backup
   - Query backup catalog (DynamoDB)
   - Latest full backup: 2 hours ago
   - WAL files available for PITR

2. Prepare recovery environment
   - Provision new database instance (AWS RDS)
   - Configure security groups
   - Allocate storage
   - Estimated time: 15 minutes

3. Restore database
   - Restore latest full backup to new instance
   - Apply WAL files to restore to point-in-time
   - Recover to T-0 (before corruption detected)
   - Duration: 90 minutes (for 100GB database)

4. Validation
   - Query test tables (verify data integrity)
   - Compare row counts to pre-failure baseline
   - Run consistency checks
   - Duration: 15 minutes

5. Application failover
   - Update application database connection string
   - Point to new database instance
   - Restart application servers (rolling restart)
   - Duration: 10 minutes

6. Post-recovery
   - Verify application functionality
   - Monitor for errors and warnings
   - Update monitoring to watch new instance
   - Create incident report

Timeline:
- T+0: Database failure detected
- T+5: On-call engineer engaged
- T+10: Recovery decision made
- T+20: New database provisioned
- T+110: Database restored and validated
- T+120: Application failover complete
- T+150: Normal operations resumed

Total RTO: ~150 minutes (2.5 hours) ✓ Meets 2-hour target

3.4 SCENARIO: DATA CENTER FAILURE
---------------------------------

Scenario: Entire primary AWS region becomes unavailable

Detection:
- Health checks fail across all services
- API requests timeout
- All availability zones down simultaneously

Response:
1. Disaster declared (CRITICAL)
2. DR team activated
3. Failover to secondary region triggered

Failover Process (RTO: 1 hour, auto-failover):
1. Automated health check detects outage
2. Route 53 health check fails (all AZs down)
3. Traffic automatically routed to secondary region
4. Replicated database in secondary region activated
5. Application servers in secondary region started
6. Estimated time: 5-10 minutes (mostly automatic)

Application Recovery:
1. Load balancer DNS updated (by Route 53)
2. Existing connections fail over to secondary
3. New connections route to secondary
4. Duration: <5 minutes

Data Consistency:
- Secondary database has hourly replicas
- Maximum data loss: up to 1 hour (RPO)
- Latest transactions may be lost
- Acceptable trade-off for availability

Post-Failover:
- Monitor secondary region for stability
- Assess primary region (when available)
- Plan data resync if primary region recovers
- Implement root cause fix
- Plan failback to primary (when stable)

3.5 SCENARIO: RANSOMWARE / SECURITY BREACH
-------------------------------------------

Scenario: Ransomware encrypts database and backups

Detection:
- Data corruption alerts trigger
- Integrity checks fail
- Recovery verification fails

Prevention Strategy:
- Air-gapped backups (isolated from network)
- Immutable backups (cannot be modified or deleted)
- Encrypted backups (even if stolen, cannot use)
- Backup verification (detect tampering)

Recovery:
1. Isolate infected systems (network quarantine)
2. Identify last clean backup
3. Restore from clean backup (likely >1 day old)
4. Verify restoration (no malware)
5. Gradually bring systems back online
6. Monitor for re-infection
7. Conduct forensic analysis

Backup Protection:
- Separate credentials for backup access
- Read-only access to backup storage
- MFA required for backup deletion
- Audit logging for all backup access
- Multiple backup copies (one offline)

3.6 SCENARIO: ACCIDENTAL DATA DELETION
--------------------------------------

Scenario: Developer accidentally runs DELETE statement on production database

Detection:
- DML audit log shows unexpected DELETE
- Row counts suddenly drop
- Alert: "High delete rate detected"

Recovery (Using PITR):
1. Alert triggers immediately
2. Determine time of DELETE statement
3. Restore database to point-in-time (before deletion)
4. Duration: <15 minutes
5. Verify data restored
6. Failover to restored database

Timeline:
- T+0: DELETE executed
- T+2: Alert fires
- T+5: Investigation begins
- T+8: Root cause identified (accidental DELETE)
- T+10: PITR restore initiated
- T+25: Database restored
- T+30: Application failover
- T+35: Data restored, normal operation resumed

RTO: 35 minutes ✓

  verified_at (TIMESTAMP)

  restore_started_at (TIMESTAMP)
  restore_completed_at (TIMESTAMP)
  duration_minutes (INTEGER)
  data_loss_minutes (INTEGER) -- How much data from last backup
  recovery_success (BOOLEAN)
  failure_reason (TEXT) -- If failed
  verified_by (UUID, FK to users)
  notes (TEXT)
  incident_id (UUID, FK) -- If related to incident
  created_at (TIMESTAMP)
  INDEX: (recovery_type, restore_completed_at)

6. OPERATIONAL PROCEDURES
================================================================================

6.1 BACKUP VERIFICATION PROCEDURE
---------------------------------

Manual backup verification (weekly):

1. List recent backups
   aws s3 ls s3://backups/daily/ --recursive | tail -10

2. Verify checksum
   sha256sum backup-2026-01-31.sql.gz.aes
   (Compare to value in backup_catalog)

3. Test decompress
   openssl enc -aes-256-cbc -d -in backup-2026-01-31.sql.gz.aes | gunzip | head -100
   (Should display SQL statements)

4. Verify backup size
   Acceptable range: 10GB-20GB (compressed)
   Alert if <5GB or >50GB (unusual)

5. Update backup_catalog
   UPDATE backup_catalog 
   SET verified_at = NOW(), status = 'VERIFIED'
   WHERE backup_id = 'backup-123'

6.2 RESTORE PROCEDURE
---------------------

Restore from backup (step-by-step):

1. Prepare staging environment
   - Provision new RDS instance
   - Configure security groups
   - Allocate storage
   - Estimated time: 15 minutes

2. Download backup
   aws s3 cp s3://backups/daily/backup-2026-01-31.sql.gz.aes .
   Estimated time: 5 minutes (depends on size)

3. Decrypt and decompress
   openssl enc -aes-256-cbc -d -in backup-2026-01-31.sql.gz.aes | gunzip > backup.sql
   Estimated time: 3 minutes

4. Restore to database
   psql -h staging-db.amazonaws.com -U admin -d clinic_db < backup.sql
   Estimated time: 90 minutes (for 100GB database)

5. Verify restoration
   - SELECT COUNT(*) FROM consultations; (compare to pre-backup count)
   - SELECT COUNT(*) FROM patients;
   - Run integrity checks
   Estimated time: 10 minutes

6. Application failover
   - Update connection string in app config
   - Restart application servers
   Estimated time: 10 minutes

7. Smoke tests
   - Login to application
   - View patient records
   - Create new consultation
   - Check dashboards
   Estimated time: 15 minutes

Total Time: ~140 minutes

6.3 INCIDENT RESPONSE - DATA LOSS
---------------------------------

If data loss detected:

1. Declare incident (CRITICAL)
2. Assess scope: which data affected, when loss detected
3. Determine point-in-time to restore to
4. Retrieve backup from that time
5. Restore to staging for verification
6. Verify data integrity
7. Plan application failover
8. Execute failover
9. Verify application functionality
10. Notify affected users (if applicable)
11. Document root cause
12. Implement preventive measures

7. SECURITY & COMPLIANCE
================================================================================

7.1 ENCRYPTION
--------------

At-Rest:
- Backup files: AES-256 encryption
- S3 bucket default encryption: AES-256
- EBS volumes: EBS encryption enabled
- Keys managed by AWS KMS
- Customer-managed CMK per tenant (tenant isolation)

In-Transit:
- S3 uploads: HTTPS/TLS 1.2+
- Cross-region replication: HTTPS encrypted
- SFTP for backup transfers (if applicable): SSH encryption
- All credentials: TLS encrypted

Key Management:
- KMS keys rotated annually
- Access to keys restricted (IAM roles)
- Audit logging for key usage
- Emergency access procedures (MFA required)

7.2 ACCESS CONTROL
------------------

Backup Access:
- Restricted to backup automation service
- Separate credentials (not application credentials)
- Read-only for application servers (can't delete backups)
- Full access only for SRE team
- MFA required for backup deletion

Backup Deletion Authorization:
- Only finance/compliance team can authorize deletion
- Requires 2 people sign-off
- Audit log recorded
- Immutable deletion receipt

Audit Logging:
- All backup operations logged
- Who created, verified, restored backup
- When and why
- Logs retained 7 years

7.3 HIPAA COMPLIANCE
--------------------

HIPAA Backup Requirements:
- Backup of medical records mandatory
- 7-year retention (minimum)
- Backup data protected with encryption
- Access control and audit logging
- Regular recovery testing

Compliance Checklist:
- ✓ Backups encrypted (AES-256)
- ✓ Retention >7 years
- ✓ Access logged and audited
- ✓ Recovery tested monthly
- ✓ Disaster recovery plan documented
- ✓ Encryption keys managed securely
- ✓ Deletion procedures documented

12. RISKS & MITIGATION
================================================================================

Risk 1: Backup Corruption Undetected
- Risk: Restore fails because backup corrupted
- Mitigation: Monthly verification, checksums, test restores
- Owner: SRE team

Risk 2: Encryption Key Loss
- Risk: Backups unrecoverable if key lost
- Mitigation: Key redundancy, secure backup, access procedures
- Owner: Security team

Risk 3: Restore Time Too Long
- Risk: RTO target not met during actual incident
- Mitigation: Regular testing, optimization, redundancy
- Owner: SRE team

Risk 4: Ransomware Encrypts Backups
- Risk: All backups compromised by malware
- Mitigation: Air-gapped backups, immutability, network isolation
- Owner: Security team

Risk 5: Insufficient Storage
- Risk: Backup storage fills, old backups deleted prematurely
- Mitigation: Capacity planning, lifecycle policies, monitoring
- Owner: SRE team
