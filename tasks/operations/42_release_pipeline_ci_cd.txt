Deployment) pipeline that automates code testing, quality checks, security

- Support multiple environments (dev, staging, production)
- Enable rapid bug fixes and feature releases

- Support rollback capability
- Achieve 30-minute release cycle

Scope:

- Automated testing (unit, integration, E2E)
- Code quality and security scanning
- Build automation and artifact management
- Staging deployment and testing
- Production deployment with rollback
- Monitoring and health checks post-deployment
- Release notes and documentation

2. CI/CD STRATEGY
================================================================================

2.1 GIT WORKFLOW
----------------

Branch Strategy: Git Flow

Main Branches:
- main: Production-ready code (stable releases)
- develop: Integration branch (next release)

Supporting Branches:
- feature/xxx: New features (from develop)
- bugfix/xxx: Bug fixes (from develop)
- hotfix/xxx: Critical fixes for production (from main)
- release/x.y: Release candidates

Workflow:

Feature Development:
1. Developer creates feature branch: feature/appointment-rescheduling
2. Make changes, commit frequently (small commits)
3. Push to GitHub
4. Create Pull Request (PR) to develop
5. PR triggers automated tests:
   - Unit tests
   - Integration tests
   - Code coverage (>70%)
   - Linting and style checks
   - Security scanning
6. Code review required (2 approvals minimum)
7. All checks pass → Merge to develop
8. Merge triggers staging deployment

Release Process:
1. Create release branch: release/1.2.0
2. Version bump (package.json, tag)
3. Update CHANGELOG.md
4. Final testing in staging
5. Create PR from release/1.2.0 → main
6. Production deployment approval
7. Merge to main → Tag v1.2.0
8. Production deployment triggered
9. Merge back to develop

Hotfix Process:
1. Create hotfix branch: hotfix/critical-bug-fix
2. Fix critical production bug
3. Bump version (patch): v1.2.1
4. Test in staging
5. Merge to main → Deploy to production
6. Merge back to develop

2.2 AUTOMATED TESTING GATES
---------------------------

Pull Request Checks (Required):

1. Unit Tests
   - Coverage: >70% code coverage
   - Duration: <5 minutes
   - Fail: PR cannot be merged
   
2. Integration Tests
   - API integration testing
   - Database integration
   - Duration: <10 minutes
   - Fail: PR cannot be merged

3. End-to-End Tests (Staging)
   - Smoke tests in staging environment
   - Key workflows tested
   - Duration: <15 minutes
   - Fail: PR cannot be merged

4. Code Linting
   - ESLint/Prettier (JavaScript)
   - Pylint/Black (Python)
   - Duration: <2 minutes
   - Fail: PR cannot be merged

5. Security Scanning
   - SAST (Static Application Security Testing)
   - Dependency vulnerability scanning (npm audit, pip audit)
   - Container image scanning
   - Secret detection (no API keys in code)
   - Duration: <10 minutes
   - Fail: PR cannot be merged

6. Code Review
   - Minimum 2 peer reviews required
   - Approval from at least 1 senior developer
   - Dismiss stale reviews on new commits

Merge Requirements:
- All 6 checks must pass
- All conversations resolved
- Linear history (no merge commits)

2.3 STAGING DEPLOYMENT
----------------------

Staging Environment:
- Identical to production (same infrastructure)
- Same configuration and data (anonymized)
- Used for final testing before production

Staging Deployment Process:

1. Merge to develop branch
2. GitHub Actions triggered automatically
3. Build Docker images
4. Run tests (all suites)
5. Deploy to staging (rolling update)
6. Run smoke tests in staging
7. Manual testing window (optional, 1-2 hours)
8. Deployment complete

Staging Tests:
- Smoke tests: core workflows (login, create patient, appointment, etc)
- Integration tests: all APIs
- Data integrity: verify no data corruption
- Performance tests: baseline comparison
- Security tests: pen testing (automated)

Approval Gates (Before Production):
- Staging tests passed (automated)
- Manual QA approval (optional)
- Product owner sign-off (optional)
- Security team approval (if security changes)

2.4 PRODUCTION DEPLOYMENT
-------------------------

Production Deployment Strategy: Rolling Update

Rolling Update Process:
1. Automated build and tests pass
2. Production deployment approval required (manual click)
3. Load balancer removes 1 server from rotation
4. Old version stopped on that server
5. New version started on that server
6. Health checks pass → Server added back to rotation
7. Repeat for each server (one at a time)
8. Duration: ~5 minutes per server (10 servers = 50 minutes)
9. Zero downtime: traffic always directed to healthy servers

Deployment Stages:
- Stage 1: Deploy to 1 server (5% traffic)
- Stage 2: Monitor for errors (15 minutes)
- If errors → Rollback to previous version
- If healthy → Deploy to remaining servers (95% traffic)
- Monitor canary for 30 minutes
- If errors → Rollback
- If healthy → Deployment complete

Rollback Triggers:
- Error rate increases by >10% post-deployment
- Critical API endpoint fails health check
- Database corruption detected
- Security alert triggered
- Manual rollback requested by ops team

Rollback Process:
1. Alert triggered (automated or manual)
2. Current version tagged as failed
3. Previous stable version identified
4. Rolling rollback: replace current with previous
5. Duration: <10 minutes
6. Health checks pass
7. Verify stability
8. Incident postmortem scheduled

Blue-Green Deployment (Alternate):
- Blue: Current production (active)
- Green: New version (staged)
- 100% traffic on Blue, 0% on Green
- All tests on Green
- When ready: Switch 100% traffic to Green
- Rollback: Switch back to Blue (instantaneous)
- Advantage: Instant rollback, disadvantage: doubles infrastructure cost

2.5 PRODUCTION DEPLOYMENT SCHEDULE
----------------------------------

Release Frequency: Weekly (Tuesdays)
- Feature releases: Every Tuesday 10 AM UTC
- Duration: 50 minutes (rolling update)
- Maintenance window: Tuesday 09:00-11:00 UTC

Hotfix Releases: As needed
- Critical bugs: Deploy immediately (any day)
- Security patches: Within 24 hours
- No scheduled maintenance window required
- Deployed outside business hours when possible

Release Blackouts: No deployments
- Fridays after 3 PM (avoid weekend issues)
- Major holidays
- Known high-traffic periods
- During scheduled maintenance windows

2.6 VERSION MANAGEMENT
----------------------

Semantic Versioning: major.minor.patch

v1.2.3

- major: Breaking changes (backward incompatible)
- minor: New features (backward compatible)
- patch: Bug fixes

Examples:
- v1.0.0: Initial release
- v1.1.0: Add new consultation module
- v1.1.1: Fix typo in consultation form
- v1.2.0: Add prescription module
- v2.0.0: Complete rewrite (breaking changes)

Release Notes:
- Major features added
- Bug fixes
- Security patches
- Known issues
- Breaking changes (for major versions)
- Migration instructions (if needed)

Version Tagging:
- Tag format: vX.Y.Z (e.g., v1.2.3)
- Release on main branch
- Annotated tag with author, date, notes
- Immutable (cannot be retagged)

3. CI/CD PIPELINE ARCHITECTURE
================================================================================

3.1 PIPELINE STAGES
-------------------

Stage 1: Trigger
- Event: Push to GitHub, PR created/updated
- Runs on: Linux Ubuntu 20.04 (GitHub Actions)
- Duration: Instant

Stage 2: Build
- Compile code (TypeScript → JavaScript, Python → bytecode)
- Build Docker images
- Push to ECR (Elastic Container Registry)
- Duration: 5 minutes

Stage 3: Test
- Unit tests (Jest, Pytest)
- Integration tests (database, APIs)
- Code coverage report
- Duration: 15 minutes

Stage 4: Quality Checks
- Linting (ESLint, Pylint)
- Code style (Prettier, Black)
- Code complexity (SonarQube)
- Duplication detection
- Duration: 5 minutes

Stage 5: Security Scanning
- SAST: SonarQube security rules
- Dependency scan: npm audit, pip audit
- Container scan: Trivy for vulnerabilities
- Secret detection: GitLeaks
- License compliance: FOSSA
- Duration: 10 minutes

Stage 6: Approval Gate
- All checks passed?
- Code review approved?
- Continue or fail?

Stage 7: Deploy to Staging
- Pull Docker image from ECR
- Deploy using Kubernetes manifests
- Run E2E tests in staging
- Health check validation
- Duration: 10 minutes

Stage 8: Approval Gate (Manual)
- Manual testing in staging (optional)
- QA sign-off
- Product owner approval
- Release manager approval

Stage 9: Deploy to Production
- Pull Docker image from ECR
- Rolling update to production servers
- Monitor health checks
- Canary monitoring (error rate, latency)
- Duration: 50 minutes (depending on server count)

Stage 10: Post-Deployment
- Smoke tests in production
- Alert: deployment complete
- Update deployment tracking
- Store release artifacts
- Send release notification

Total Pipeline Time: 30-100 minutes (depending on branch)
- Feature branch to staging: ~40 minutes
- Staging to production: ~50 minutes

3.3 DOCKERFILE
--------------

Multi-stage Docker build:

```dockerfile
# Stage 1: Build
FROM node:18-alpine AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

# Stage 2: Runtime
FROM node:18-alpine

RUN apk add --no-cache dumb-init

WORKDIR /app

# Copy only necessary files from builder
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package*.json ./

# Security: Non-root user
RUN addgroup -g 1001 -S nodejs
RUN adduser -S nodejs -u 1001
USER nodejs

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
  CMD node /app/health.js

ENTRYPOINT ["/usr/sbin/dumb-init", "--"]
CMD ["node", "dist/index.js"]
```

Image Size: ~150MB
Base Image: Alpine Linux (small, secure)
Multi-stage: Reduces final image size

4. PIPELINE CONFIGURATION (GitHub Actions)
================================================================================

.github/workflows/ci-cd.yml:

```yaml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [develop]

jobs:
  test:
    runs-on: ubuntu-20.04
    services:
      postgres:
        image: postgres:14
        env:
          POSTGRES_PASSWORD: postgres
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
    - uses: actions/checkout@v3
    
    - name: Set up Node.js
      uses: actions/setup-node@v3
      with:
        node-version: '18'
        cache: 'npm'
    
    - name: Install dependencies
      run: npm ci
    
    - name: Run linting
      run: npm run lint
    
    - name: Run unit tests
      run: npm run test:unit
    
    - name: Run integration tests
      run: npm run test:integration
      env:
        DATABASE_URL: postgresql://postgres:postgres@localhost:5432/test_db
    
    - name: Upload coverage
      uses: codecov/codecov-action@v3
      with:
        files: ./coverage/coverage-final.json
        fail_ci_if_error: true
    
    - name: Security scanning
      run: |
        npm audit --audit-level=moderate || true
        npx snyk test --severity-threshold=high || true
    
    - name: SonarQube scan
      uses: SonarSource/sonarcloud-github-action@master
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  
  build:
    needs: test
    runs-on: ubuntu-20.04
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    outputs:
      image-tag: ${{ steps.image.outputs.tag }}
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Configure AWS credentials
      uses: aws-actions/configure-aws-credentials@v2
      with:
        aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
        aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        aws-region: us-east-1
    
    - name: Login to Amazon ECR
      id: login-ecr
      uses: aws-actions/amazon-ecr-login@v1
    
    - name: Build Docker image
      id: image
      env:
        ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
        ECR_REPOSITORY: consultation-api
        IMAGE_TAG: ${{ github.sha }}
      run: |
        docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
        docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
        echo "tag=$ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> $GITHUB_OUTPUT
    
    - name: Scan image for vulnerabilities
      run: |
        docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
          aquasec/trivy image ${{ steps.image.outputs.tag }}
  
  deploy-staging:
    needs: build
    runs-on: ubuntu-20.04
    if: github.event_name == 'push' && github.ref == 'refs/heads/develop'
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Deploy to staging
      env:
        KUBECONFIG: ${{ secrets.KUBECONFIG }}
        IMAGE_TAG: ${{ needs.build.outputs.image-tag }}
      run: |
        kubectl set image deployment/consultation-api \
          consultation-api=$IMAGE_TAG \
          --record -n staging
        kubectl rollout status deployment/consultation-api -n staging
    
    - name: Run E2E tests
      run: npm run test:e2e:staging
    
    - name: Notify Slack
      uses: slackapi/slack-github-action@v1
      with:
        webhook-url: ${{ secrets.SLACK_WEBHOOK }}
        payload: |
          {
            "text": "Staging deployment complete: ${{ needs.build.outputs.image-tag }}"
          }
  
  deploy-production:
    needs: build
    runs-on: ubuntu-20.04
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    environment:
      name: production
      url: https://api.clinic.com
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Approve production deployment
      uses: actions/github-script@v6
      with:
        script: |
          console.log('Production deployment requires manual approval');
    
    - name: Deploy to production
      env:
        KUBECONFIG: ${{ secrets.KUBECONFIG }}
        IMAGE_TAG: ${{ needs.build.outputs.image-tag }}
      run: |
        kubectl set image deployment/consultation-api \
          consultation-api=$IMAGE_TAG \
          --record -n production
        kubectl rollout status deployment/consultation-api -n production \
          --timeout=10m
    
    - name: Run production smoke tests
      run: npm run test:smoke:production
    
    - name: Record deployment
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      run: |
        gh release create ${{ github.sha }} \
          --title "Release ${{ github.sha }}" \
          --notes "$(cat CHANGELOG.md | head -20)"
    
    - name: Notify team
      uses: slackapi/slack-github-action@v1
      with:
        webhook-url: ${{ secrets.SLACK_WEBHOOK }}
        payload: |
          {
            "text": "Production deployment complete: ${{ needs.build.outputs.image-tag }}"
          }
```
