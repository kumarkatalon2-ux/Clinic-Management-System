3.1 INDEXING STRATEGY
---------------------

Composite Indexes (Multi-column):
```sql
-- Appointments: commonly filtered by date range
CREATE INDEX idx_appointments_clinic_date 
ON appointments(clinic_id, appointment_date DESC);

-- Consultations: tenant + patient + date
CREATE INDEX idx_consultations_tenant_patient_date 
ON consultations(tenant_id, patient_id, created_at DESC);

-- Prescriptions: patient + status
CREATE INDEX idx_prescriptions_patient_status 
ON prescriptions(patient_id, status, created_at DESC);

-- Audit logs: tenant + user + action
CREATE INDEX idx_audit_logs_tenant_user_action 
ON audit_logs(tenant_id, user_id, action_type, created_at DESC);
```

Partial Indexes (Conditional):
```sql
-- Only index active (not deleted) records
CREATE INDEX idx_active_appointments 
ON appointments(clinic_id, appointment_date) 
WHERE deleted_at IS NULL;

-- Only index pending invoices
CREATE INDEX idx_pending_invoices 
ON invoices(patient_id, due_date) 
WHERE status = 'OUTSTANDING';

-- Only index enabled users
CREATE INDEX idx_active_users 
ON users(tenant_id, email) 
WHERE is_active = true;
```

Text Indexes (Full-text search):
```sql
-- Patient names full-text search
CREATE INDEX idx_patient_names_fulltext 
ON patients USING GIN(to_tsvector('english', first_name || ' ' || last_name));

-- Clinical notes full-text search
CREATE INDEX idx_clinical_notes_fulltext 
ON clinical_notes USING GIN(to_tsvector('english', note_content));
```

Index Stats:
- Total indexes: 50+
- Index size: ~5GB (10% of total database)
- Regular maintenance: REINDEX weekly

Index Tuning:
- Monitor unused indexes (drop them)
- Monitor duplicate indexes (consolidate)
- Monitor slow queries (add indexes)
- EXPLAIN ANALYZE for query plans

3.2 QUERY OPTIMIZATION
----------------------

Bad Query Example:
```sql
-- N+1 problem: queries database once per consultation
SELECT * FROM consultations WHERE clinic_id = ? LIMIT 100;
FOR EACH consultation:
  SELECT * FROM prescriptions WHERE consultation_id = ?;
  SELECT * FROM diagnoses WHERE consultation_id = ?;
```

Good Query (JOIN):
```sql
-- Single query with JOINs
SELECT c.*, p.*, d.* 
FROM consultations c
LEFT JOIN prescriptions p ON c.id = p.consultation_id
LEFT JOIN diagnoses d ON c.id = d.consultation_id
WHERE c.clinic_id = ? 
LIMIT 100;
```

Better Query (Pagination):
```sql
-- Add pagination to limit result size
SELECT c.id, c.patient_id, c.chief_complaint, c.created_at,
       COUNT(DISTINCT p.id) as rx_count,
       COUNT(DISTINCT d.id) as diagnosis_count
FROM consultations c
LEFT JOIN prescriptions p ON c.id = p.consultation_id
LEFT JOIN diagnoses d ON c.id = d.consultation_id
WHERE c.clinic_id = ? AND c.created_at >= ? AND c.created_at < ?
GROUP BY c.id, c.patient_id, c.chief_complaint, c.created_at
ORDER BY c.created_at DESC
LIMIT 50 OFFSET 0;
```

Common Optimizations:
1. Use LIMIT and OFFSET (avoid fetching all rows)
2. Select only needed columns (avoid SELECT *)
3. Use INNER JOIN not OUTER when possible
4. Avoid function calls in WHERE clause
5. Use UNION ALL instead of UNION (no distinct needed)
6. Batch inserts (insert multiple rows at once)
7. Use EXPLAIN ANALYZE to check query plans

3.3 PARTITIONING STRATEGY
-------------------------

Table Partitioning by Date (for large tables):

```sql
-- Partition consultations by month
CREATE TABLE consultations (
  id UUID PRIMARY KEY,
  tenant_id UUID,
  patient_id UUID,
  created_at TIMESTAMP,
  ...
) PARTITION BY RANGE (DATE_TRUNC('month', created_at));

-- Create partitions (monthly)
CREATE TABLE consultations_2025_01 PARTITION OF consultations
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
  
CREATE TABLE consultations_2025_02 PARTITION OF consultations
  FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- Automatic partition pruning: query only relevant partition
SELECT * FROM consultations 
WHERE created_at >= '2025-01-15' AND created_at < '2025-01-31';
-- Only reads from consultations_2025_01
```

Partitioning Benefits:
- Faster queries (smaller tables)
- Parallel query execution
- Easier archival (drop old partitions)
- Faster backups (per partition)
- Reduced index size

Partitioning Candidates:
- consultations (billions of rows, monthly partition)
- audit_logs (billions of rows, monthly partition)
- appointments (billions of rows, quarterly partition)
- payments (millions of rows, yearly partition)

3.4 MATERIALIZED VIEWS FOR REPORTING
-------------------------------------

Complex Reporting Query (Slow):
```sql
SELECT c.clinic_id, COUNT(DISTINCT a.id) as appointments_count,
       COUNT(DISTINCT cons.id) as consultations_count,
       COUNT(DISTINCT p.id) as patients_count,
       SUM(inv.total_due) as revenue
FROM clinics c
LEFT JOIN appointments a ON c.id = a.clinic_id
LEFT JOIN consultations cons ON a.id = cons.appointment_id
LEFT JOIN patients p ON a.patient_id = p.id
LEFT JOIN invoices inv ON cons.id = inv.consultation_id
WHERE a.created_at >= DATE_TRUNC('day', NOW())
GROUP BY c.clinic_id;
-- Takes 30+ seconds (complex aggregation)
```

Solution: Materialized View:
```sql
CREATE MATERIALIZED VIEW clinic_daily_metrics AS
SELECT c.clinic_id, 
       COUNT(DISTINCT a.id) as appointments_count,
       COUNT(DISTINCT cons.id) as consultations_count,
       COUNT(DISTINCT p.id) as patients_count,
       SUM(inv.total_due) as revenue
FROM clinics c
LEFT JOIN appointments a ON c.id = a.clinic_id
LEFT JOIN consultations cons ON a.id = cons.appointment_id
LEFT JOIN patients p ON a.patient_id = p.id
LEFT JOIN invoices inv ON cons.id = inv.consultation_id
WHERE a.created_at >= DATE_TRUNC('day', NOW())
GROUP BY c.clinic_id;

-- Refresh every hour (background job)
REFRESH MATERIALIZED VIEW CONCURRENTLY clinic_daily_metrics;

-- Query is now instant (<100ms)
SELECT * FROM clinic_daily_metrics WHERE clinic_id = ?;
```

4. CACHING STRATEGY
================================================================================

4.1 MULTI-LAYER CACHING
-----------------------

Layer 1: Database Query Cache (Redis)
- Cache time: 1-5 minutes
- Invalidation: On write (DELETE from cache)
- Hit rate target: >80%
- Examples:
  - Patient details (5 min TTL)
  - Clinic configuration (30 min TTL)
  - Insurance plan details (60 min TTL)

Layer 2: Application-level Cache (Redis)
- Cache time: 5-30 minutes
- Invalidation: Time-based (TTL)
- Hit rate target: >70%
- Examples:
  - Rendered dashboards (10 min)
  - Report results (30 min)
  - Doctor schedules (5 min)

Layer 3: HTTP Cache (Browser/CDN)
- Cache time: 5-60 minutes
- Invalidation: Time-based or manual
- Examples:
  - Static assets (CSS, JS) - 1 day
  - Images and documents - 24 hours
  - API responses - 5-10 min

4.2 CACHE INVALIDATION STRATEGIES
---------------------------------

Write-Through Caching:
```python
# Write to database first, then cache
def create_patient(patient_data):
    patient = database.insert('patients', patient_data)
    cache.set(f'patient:{patient.id}', patient, ttl=300)
    return patient
```

Cache-Aside (Lazy Loading):
```python
def get_patient(patient_id):
    # Try cache first
    patient = cache.get(f'patient:{patient_id}')
    if patient:
        return patient
    
    # Cache miss: fetch from database
    patient = database.query('patients', id=patient_id)
    
    # Store in cache for next request
    cache.set(f'patient:{patient_id}', patient, ttl=300)
    return patient
```

Invalidation on Write:
```python
def update_patient(patient_id, updates):
    patient = database.update('patients', patient_id, updates)
    # Invalidate cache
    cache.delete(f'patient:{patient_id}')
    return patient
```

Pattern: Invalidate Related Caches:
```python
def create_consultation(consultation_data):
    consultation = database.insert('consultations', consultation_data)
    
    # Invalidate related caches
    cache.delete(f'patient:{consultation.patient_id}:consultations')
    cache.delete(f'doctor:{consultation.doctor_id}:consultations')
    cache.delete(f'clinic:{consultation.clinic_id}:metrics')
    
    return consultation
```

4.3 REDIS OPTIMIZATION
----------------------

Redis Configuration:
```
# Redis server settings
maxmemory 2gb                    # Max memory (2GB)
maxmemory-policy allkeys-lru     # Eviction policy: LRU
appendonly yes                   # Persistence
appendfsync everysec             # Sync every second
```

Connection Pooling:
```python
from redis import ConnectionPool

pool = ConnectionPool(
    host='redis.example.com',
    port=6379,
    max_connections=50,  # Max 50 connections
    health_check_interval=30
)
redis_client = Redis(connection_pool=pool)
```

Batch Operations:
```python
# Bad: Pipeline inefficient
for patient_id in patient_ids:
    cache.get(f'patient:{patient_id}')  # One round-trip per call

# Good: Use pipeline (batch)
pipe = redis_client.pipeline()
for patient_id in patient_ids:
    pipe.get(f'patient:{patient_id}')
results = pipe.execute()  # Single round-trip for all
```

Cache Monitoring:
```
Redis INFO stats:
- hit_rate = hits / (hits + misses) [Target: >90%]
- evicted_keys [Should be minimal]
- used_memory [Monitor for overflow]
- connected_clients [Check for leaks]
```

4.4 CACHE WARMING
-----------------

Pre-populate Cache:
```python
def warm_cache():
    """Called on startup and hourly"""
    # Cache all active clinics
    clinics = database.query('clinics', is_active=True)
    for clinic in clinics:
        cache.set(f'clinic:{clinic.id}', clinic, ttl=3600)
    
    # Cache popular insurance plans
    plans = database.query('insurance_plans', is_popular=True)
    for plan in plans:
        cache.set(f'insurance_plan:{plan.id}', plan, ttl=3600)
    
    # Cache doctor schedules
    doctors = database.query('doctors', is_active=True)
    for doctor in doctors:
        schedule = database.query('doctor_schedules', doctor_id=doctor.id)
        cache.set(f'doctor_schedule:{doctor.id}', schedule, ttl=300)
```

6.4 BROWSER CACHING
------------------

Set cache headers:
```
Cache-Control: public, max-age=31536000  // Static assets (1 year)
Cache-Control: public, max-age=3600      // API responses (1 hour)
Cache-Control: no-cache, no-store        // Dynamic content
```

Service Worker:
```javascript
// Cache API responses
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request)
      .then((response) => response || fetch(event.request))
      .then((response) => {
        const clonedResponse = response.clone();
        caches.open('api-cache').then((cache) => {
          cache.put(event.request, clonedResponse);
        });
        return response;
      })
  );
});
```

7.2 LOAD BALANCING
------------------

Round-robin distribution:
```
Request 1 → Server 1 (CPU: 45%)
Request 2 → Server 2 (CPU: 40%)
Request 3 → Server 3 (CPU: 42%)
Request 4 → Server 1 (CPU: 46%)
```

Sticky sessions (if needed):
```
User Session maintained on same server
User 1 → Always routes to Server 1
User 2 → Always routes to Server 2
```
