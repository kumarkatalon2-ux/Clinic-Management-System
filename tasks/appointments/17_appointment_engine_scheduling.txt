OBJECTIVE
---------
Implement appointment scheduling engine responsible for checking availability,
booking appointments, managing conflicts, handling cancellations, and
coordinating resources (doctors, rooms, staff).

BUSINESS LOGIC
--------------
Appointment Engine Purpose:

The appointment engine is the "brain" of scheduling:
- Checks what appointments are available
- Books confirmed appointments
- Prevents double-booking (doctor can't be in 2 rooms)
- Checks resource availability (rooms, equipment)
- Handles cancellations and rescheduling
- Enforces clinic policies (advance booking, buffer times)
- Manages patient confirmations

Appointment Lifecycle:

REQUESTED → CONFIRMED → IN_PROGRESS → COMPLETED
    ↓
 CANCELLED

Request: Patient wants appointment
  - Patient selects date, time, doctor
  - System checks availability
  - Request created (pending confirmation)

Confirmed: Patient confirmed appointment
  - Patient confirms via email/SMS
  - Appointment locked (patient can't easily cancel)
  - Calendar slots reserved
  - Reminders scheduled

In Progress: Appointment happening now
  - Patient checked in
  - Vital signs recorded
  - Doctor seeing patient
  - Notes being documented

Completed: Appointment done
  - Visit complete
  - Clinical notes documented
  - Follow-up scheduled (if needed)
  - Billing processed

Cancelled: Appointment cancelled
  - Patient cancelled (within policy window)
  - Doctor cancelled (automatic reschedule)
  - No-show (patient didn't show up)
  - Slot returned to availability

AVAILABILITY CHECKING
---------------------
When checking for available slots:

System considers:

1. CLINIC HOURS
   Clinic is closed on Sunday?
   → Can't book on Sunday

2. OPERATING HOURS
   Clinic hours: 8am-5pm
   → Can't book at 6pm

3. DOCTOR AVAILABILITY
   Doctor working on date?
   → Check doctor_schedules table
   
   Doctor on vacation?
   → Check doctor_leaves table
   
   Doctor hours: 9am-12pm, 1pm-5pm?
   → Can't book 12pm-1pm (lunch)

4. EXISTING APPOINTMENTS
   Doctor already has appointment 2-3pm?
   → Can't book overlapping time

5. BUFFER TIMES
   General visit: 30 minutes + 5 min before + 5 min after
   → Need 40 minutes total blocked time

6. ROOM AVAILABILITY
   Exam room available?
   → Can't book if room already used

7. RESOURCE AVAILABILITY
   Nurse required but only doctor available?
   → Wait for nurse

8. CLINIC POLICIES
   Book max 90 days in advance?
   → Reject requests >90 days out
   
   Book min 24 hours in advance?
   → Reject requests <24 hours

9. PATIENT STATUS
   Patient blocked (excessive no-shows)?
   → Require staff approval

10. PATIENT HISTORY
    Prone to no-shows?
    → May require deposit or confirmation

Availability Query Process:

1. USER REQUESTS: "Show me available times for Feb 15"

2. SYSTEM CHECKS:
   - Clinic open on Feb 15? YES
   - Doctor working Feb 15? YES
   - Doctor on leave? NO
   - Operating hours: 8am-5pm
   - Doctor hours: 8am-5pm
   - Lunch: 12-1pm
   - Existing appointments: 9-10am, 11am-12pm, 2-3pm, 4-5pm

3. CALCULATE AVAILABLE SLOTS (30-min visit):
   - 8am: AVAILABLE
   - 8:30am: AVAILABLE
   - 9am: OCCUPIED (existing appointment)
   - 9:30am: OCCUPIED (existing appointment)
   - 10am: AVAILABLE
   - 10:30am: AVAILABLE
   - 11am: OCCUPIED (existing appointment)
   - 11:30am: OCCUPIED (buffer for 11am appointment)
   - 12pm: LUNCH
   - 1pm: AVAILABLE
   - 1:30pm: AVAILABLE
   - 2pm: OCCUPIED (existing appointment)
   - 3pm: AVAILABLE (buffer added)
   - 3:30pm: AVAILABLE
   - 4pm: OCCUPIED (existing appointment)
   - 4:30pm: AVAILABLE (buffer added)

4. RETURN TO USER:
   Available times: [8am, 8:30am, 10am, 10:30am, 1pm, 1:30pm, 3pm, 3:30pm, 4:30pm]

DOUBLE-BOOKING PREVENTION
-------------------------
Critical Issue: Doctor can't be in two places at once

Scenario: Dr. Smith has appointment 9-10am in Room 1

If system tries to book Dr. Smith 9:30-10:30am in Room 2:
→ CONFLICT! Dr. Smith already in Room 1 at 9:30am

Prevention Logic:

Availability Query:
  FOR each existing appointment with same doctor
    IF existing.start_time < requested.end_time AND
       existing.end_time > requested.start_time
    THEN CONFLICT
    RETURN unavailable

Example Times for 30-min appointment with 5-min buffer:

Existing: 9am-10am (appointment) + 5min buffer = 9am-10:05am
Request: 9:30am-10am
  → Overlaps with 9am-10:05am block
  → REJECTED

Request: 10:05am-10:35am
  → Starts exactly when existing appointment + buffer ends
  → ACCEPTED (if no other conflicts)

Request: 10am-10:30am
  → Starts before buffer ends (at 10:05am)
  → REJECTED

Room Double-Booking Prevention:

Similar logic for rooms:

FOR each appointment using room
  IF appointment.start < requested.end AND
     appointment.end > requested.start
  THEN CONFLICT
  RETURN unavailable

Multiple Resource Conflicts:

Appointment requires: Doctor + Room + Nurse

Must check conflicts for ALL resources:

checkConflict(doctor, date, startTime, endTime):
  → Checks doctor availability

checkConflict(room, date, startTime, endTime):
  → Checks room availability

checkConflict(nurse, date, startTime, endTime):
  → Checks nurse availability

If ANY resource conflicts → Reject request

CANCELLATION & RESCHEDULING
----------------------------
Patient Cancellation:

CREATE TABLE cancellations (
  id UUID PRIMARY KEY,
  appointment_id UUID NOT NULL,
  cancelled_by UUID NOT NULL,  -- Patient or staff
  cancelled_at TIMESTAMP,
  cancellation_reason VARCHAR(255),
  cancellation_type VARCHAR(50),  -- PATIENT, CLINIC, NO_SHOW
  fee_charged DECIMAL,  -- Late cancellation fee
  
  created_at TIMESTAMP
);

Cancellation Policy Enforcement:

Current time: 2024-02-14 10:00am
Appointment: 2024-02-15 08:00am (24 hours away)

Cancellation Policy: Must cancel 24+ hours before

Can patient cancel? YES (exactly 24 hours notice)

Later: 2024-02-15 09:00am
Appointment: 2024-02-15 10:00am (1 hour away)

Can patient cancel? NO (less than 24 hours notice)
→ Late cancellation fee charged: $25

6. Notification sent to clinic staff

System:

OVERBOOKING & WAITLIST
---------------------
Overbooking Strategy (10% allowed):

Clinic capacity: 20 patients per day
Overbooking: 10% = 2 extra patients

Total allowed: 22 patients

Why? Account for no-shows (~10% don't show)

If 2 patients cancel, clinic still has 20 patients (good utilization)
If all 22 show, slight overbooking (acceptable for clinic)

Overbooking Queue:

CREATE TABLE overbooked_appointments (
  id UUID PRIMARY KEY,
  appointment_id UUID NOT NULL,
  overbooking_position INT,  -- 1st overbooked, 2nd overbooked, etc.
  created_at TIMESTAMP
);

When booking appointment #21 (within overbooking):
→ Marked as overbooking_position = 1

When booking appointment #22 (within overbooking):
→ Marked as overbooking_position = 2

If patient #20 cancels:
→ Patient at overbooking_position = 1 moves to regular slot
→ Patient at overbooking_position = 2 moves to position 1

Waitlist:

If clinic fully booked (including overbooking):

POST /appointments/waitlist
{
  "patientId": "uuid-patient",
  "clinicId": "uuid-clinic",
  "preferredDate": "2024-02-15",
  "preferredDoctor": "uuid-doctor"
}

System:
1. Adds to waitlist
2. Monitors cancellations
3. Auto-books if slot becomes available
4. Notifies patient of availability

Waitlist Table:

CREATE TABLE waitlists (
  id UUID PRIMARY KEY,
  patient_id UUID NOT NULL,
  clinic_id UUID NOT NULL,
  preferred_date DATE,
  doctor_id UUID,
  position INT,  -- 1st on waitlist, 2nd, etc.
  status VARCHAR(50),  -- WAITING, OFFERED, BOOKED, EXPIRED
  created_at TIMESTAMP,
  offered_at TIMESTAMP,
  offer_expiration TIMESTAMP
);
