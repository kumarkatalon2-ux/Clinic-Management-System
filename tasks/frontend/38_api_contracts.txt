backend services. It standardizes request/response formats, status codes, error

specification serves as the contract between frontend and backend teams, enabling

2. API DESIGN PRINCIPLES
================================================================================

2.1 REST CONVENTIONS
- Resource-based URLs: /api/v1/patients, /api/v1/patients/{id}/consultations
- HTTP methods: GET (read), POST (create), PUT (update), DELETE (delete)
- Status codes: 200 (success), 201 (created), 400 (bad request), 403 (forbidden), 404 (not found), 500 (server error)
- Stateless: Each request contains all info needed (no session state)

2.2 NAMING CONVENTIONS
- Endpoints: Lowercase, kebab-case: /api/v1/appointment-slots
- Fields: camelCase: patientId, appointmentDate, visitType
- Timestamps: ISO 8601: 2026-01-31T14:30:00Z
- IDs: UUID v4 format
- Errors: Standard error object with code, message, details

2.3 VERSIONING
- URL versioning: /api/v1/, /api/v2/ for major versions
- Backward compatibility: Minor changes don't require version bump
- Deprecation: Old endpoints deprecated for 6 months before removal
- Support: Support current + 1 previous major version

================================================================================
3. REQUEST & RESPONSE STANDARDS
================================================================================

3.1 SUCCESS RESPONSE FORMAT
Standard Success (200 OK):
{
  "status": "success",
  "code": 200,
  "data": { ... },
  "timestamp": "2026-01-31T14:30:00Z"
}

Paginated Response (200 OK):
{
  "status": "success",
  "code": 200,
  "data": [ ... ],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalPages": 5,
    "totalRecords": 100
  },
  "timestamp": "2026-01-31T14:30:00Z"
}

3.2 ERROR RESPONSE FORMAT
Error Response (4xx or 5xx):
{
  "status": "error",
  "code": 400,
  "error": {
    "type": "VALIDATION_ERROR",
    "message": "Patient not found",
    "details": {
      "patient_id": "Invalid UUID format"
    }
  },
  "timestamp": "2026-01-31T14:30:00Z"
}

3.3 AUTHENTICATION HEADER
All requests require:
Authorization: Bearer {JWT_TOKEN}

Token Format (JWT):
{
  "sub": "user_id",
  "iat": 1234567890,
  "exp": 1234571490,
  "roles": ["provider", "clinic_manager"],
  "clinic_id": "clinic_id"
}

3.4 COMMON HEADERS
- Content-Type: application/json
- Accept: application/json
- X-Request-ID: Unique request ID for tracing
- X-Idempotency-Key: For idempotent operations (POST)
- Accept-Language: Language preference (en-US, es-MX)

Pagination:
- Query: ?page=1&pageSize=20&sortBy=createdAt&sortOrder=desc

6. ERROR HANDLING & STATUS CODES
================================================================================

6.1 HTTP STATUS CODES
- 200 OK: Successful GET, PUT
- 201 Created: Successful POST
- 204 No Content: Successful DELETE
- 400 Bad Request: Validation error, malformed request
- 401 Unauthorized: Authentication required or failed
- 403 Forbidden: Authenticated but not authorized
- 404 Not Found: Resource not found
- 409 Conflict: Resource conflict (e.g., duplicate)
- 429 Too Many Requests: Rate limit exceeded
- 500 Internal Server Error: Server error
- 503 Service Unavailable: Server maintenance or overloaded

6.2 ERROR TYPES
- VALIDATION_ERROR: Field validation failed
- AUTHENTICATION_FAILED: Credentials invalid
- AUTHORIZATION_FAILED: Insufficient permissions
- RESOURCE_NOT_FOUND: Entity not found
- DUPLICATE_RECORD: Unique constraint violation
- BUSINESS_LOGIC_ERROR: Business rule violated
- EXTERNAL_SERVICE_ERROR: Third-party service error
- DATABASE_ERROR: Database operation failed
- RATE_LIMIT_EXCEEDED: Too many requests

}

Retry Policy:
- Retry on 5xx errors
- Exponential backoff: 1s, 4s, 16s, 64s (max)
- Max retries: 10
- Delivery confirmation: Webhook consumer must respond 2xx
